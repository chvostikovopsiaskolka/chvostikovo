# Web form viewport stability — v274 (16 October 2026)

Reported on iPhone: choosing a dog's sex/neuter status after dismissing the keyboard, or autofilling the owner's name, displaced the visible form. Screenshots show native iOS pickers separated from their controls. Exact OS-level geometry cannot be reproduced in the available DOM runtime; do not describe it as a confirmed WebKit root cause or claim physical-device verification.

The actual shared FormDialog used a fixed 50%/50% position with translation on both axes, animated zoom, and the entire dialog as its scroll container. Radix default opening focus also targeted the first input. These concrete layout/focus mechanisms are changed locally:

- Mobile (<640px): top anchored, centered using left/right margins, no transform/translate/scale/zoom animation on the native-select ancestor.
- One inner scroll container; heading and close control stay outside it. Desktop retains its centered placement.
- VisualViewport resize/scroll updates only CSS properties for available height and offset. RAF batches changes, listeners are removed on close, pinch zoom is not counteracted. No field recentering, scrollIntoView, scroll reset, or React render on each viewport event.
- Opening focuses the title with preventScroll, retaining Radix focus trapping and Escape/close behavior, without opening the keyboard automatically.
- Owner name/phone autocomplete remains available. Both dog name fields explicitly opt out of human-contact autocomplete.
- Same shared dialog covers application, short Slovak enquiry, puppy/lead landing and English enquiry. Inline forms retain their layout; the dog-name autocomplete change also applies inline.

`scripts/form-dialog-stability-checks.tsx` mounts the actual Radix FormDialog and verifies single/two-dog content, initial heading focus, viewport shrink/restore/offset, native select focus, silent-autofill value and DOM identity, scroll preservation, zoom and listener cleanup. It is part of check:critical-forms. This is DOM verification, not an iOS keyboard/picker geometry emulator. Existing critical submit/autofill checks and TypeScript validation must also pass. No live form submission or customer SMS is necessary for this layout change.

Rollback baseline: main 2d26ce1ed406bbfe6772b4db2d2100ca7035bc0a, remote backup-web-before-form-stability-v274-20261016. Revert only this feature's commit after checking later edits; do not deploy an old whole-tree snapshot over newer changes. Supabase, admin, customer portal, CRM, recovery, SMS and conversion code are unchanged.


## Update v293 — 17 October 2026, iOS keyboard reveals background under form

Actual physical iPhone screenshots at 14:13–14:14 after Web v292 still show the modal ending hundreds of pixels ABOVE the keyboard, large blurred underlying page exposed, and scroll leakage behind the form. **This proves the v292 assumption “never use visualViewport.offsetTop” was insufficient**, despite passing simulated DOM tests. The native WebKit visual viewport may independently pan when a focused text field opens the keyboard; a fixed modal defined only against the layout viewport can be pushed high above the visible keyboard.

v293 is a new bounded hypothesis implemented in the existing shared FormDialog, not a guarantee of physical Safari success. For a clearly open keyboard (captured prekeyboard height minus visible viewport height >150px), and **only** during that state, compensate the visual viewport's `offsetTop` (clamp to actual hidden region). Switch the mobile dialog from a naturally sized floating card into an edge-to-edge **sheet**, with height equal to visible viewport above the keyboard and no bottom/side gutters. Restore the original 12px side gutters, natural height and rounded corners after keyboard dismissal. Keep a single independently scrollable `.form-dialog-scroll`, preserve focused input/autofill values and 16px typography; moving text into view may modify the inner scroller **only**. Block modal-exterior mobile touch scroll and scroll chaining. Do not use body transforms, re-mount input nodes, window.scrollTo, per-field positioned modals or additional server requests.

Acceptance gate remains unproven until a physical iPhone Safari verification: fill first dog's name/plemeno/vek/alergie/povaha and second-dog fields, keyboard open/close, auto-fill, select usage; while focused, white modal must reach keyboard top without exposing large green/blur background, underlying web must not pan, active caret must remain visible, and scroll must move exclusively inside form. Also check Android Chrome, responsive and EN. Simulated tests/Pages deploy are source or automation evidence only. Preserve explicit backup branch and rollback instructions. If physical WebKit behavior still fails, halt further speculative production CSS patches and obtain measured `visualViewport.height/offsetTop`, document scrollY, keyboard position, dialog/scroller rectangles in a test device before another deployment.

## Update v292 — 17 October 2026, iOS Safari application keyboard and native picker

The 13:26–13:27 user screenshots show an actual black native sex picker and long-form contents disappearing or moving to a preceding field while the keyboard is open. This is a real physical iPhone regression; its precise internal WebKit cause cannot be proven from screenshots alone. The previous v278 modal measured `visualViewport.offsetTop` and applied it directly to its fixed `top` on every viewport scroll/resize. When Safari shifts the visual viewport during native keyboard/autofill, this creates a second, application-driven movement of the whole dialog. This source-level causal mechanism is fixed in v292.

Binding invariants for ALL shared web forms, especially 1/2-dog application and contact/EN forms:

- The form modal's mobile `top` is a stable safe-area offset independent of `visualViewport.offsetTop`, scrollY, focus, blur, keyboard and autofill. No transform, centered translation, animation or global scroll/scrollIntoView may move the portal while entering data. `visualViewport.height` only updates available **height**, batched by animation frame.
- Only the existing `.form-dialog-scroll` scrolls within the modal. When a real editable text field or textarea gains focus or the keyboard viewport resizes, move only this inner scroller **if the focused field falls outside its visible rectangle**. Never reset inner scroll on blur, autofill, keyboard dismissal or picker selection; never try to reposition a native picker while it is open. Focus remains on the original element and its value remains unchanged. Keyboard-dismiss recovery cannot leave the content clipped after resizing.
- The two-choice dog sex and neuter fields use accessible inline radio choices (Pes/Suka, Áno/Nie) for both dog blocks, retaining the same `FormData` field names/values/required validation and eliminating the full-screen native OS selection sheet for those fields. Other native `select` fields use an explicit light color scheme; OS-managed pickers may still differ by system/browser and need physical validation.
- Never disable name/phone autofill. Its silent value changes and auto blur must not trigger form remount or forced scroll. Retain input 16px to avoid iOS automatic zoom, real keyboard `:focus-visible`, 44px touch targets and form progress/consent/submit telemetry. The shared dialog's layout applies equally to contact, lead, puppy, enrollment and EN.
- Run the existing `scripts/form-dialog-stability-checks.tsx`, critical forms, form autofill and a real iOS Safari (autofill, Pes/Suka, selection, age, allergies, long textarea, keyboard open/close) and Android Chrome before claiming the complete behavior is proven. Synthetic DOM tests cannot simulate Apple's native keyboard or autofill animation.

Do not introduce a visual-viewport top-offset fix again, a body/window scroll listener, a second nested scroll owner, a new modal or a replacement upload/form submission handler. This change is UI only: no CRM, Edge, RLS, lead attribution, conversion, UTM, SMS or backend mutation. Rollback safely to the prior Git commit only after checking later web changes.
